## CRITICAL FIX 1: Syncthing must run inside Setu

### Problem (found 2026-11-24)

On the Windows laptop, Syncthing runs as a separate thing that Setu does not own:

- Scheduled task `\Syncthing (Setu)` ("Syncthing for Setu, tailnet only"), trigger: at logon,
  user `Rajeev`, no author. It runs
  `powershell.exe -NoProfile -WindowStyle Hidden -ExecutionPolicy Bypass -File %LOCALAPPDATA%\Setu\start-syncthing.ps1`.
- That script starts the WinGet copy of `syncthing.exe serve --no-browser --no-console
  --home=%LOCALAPPDATA%\Syncthing`.
- `%LOCALAPPDATA%\Setu\syncthing-gui-password.txt` holds the Syncthing GUI password in plain text.
- None of this is in the repo or the installer (`packaging/windows/setu.iss`). It was set up by
  hand on 2026-11-20 22:27, so the user never agreed to it through Setu and Setu cannot show,
  stop or remove it.
- At logon Syncthing starts before Tailscale is up, so binding `100.123.109.119:22000` fails
  ("The requested address is not valid in its context") and it retries for about two minutes.
- Setu itself is split too: `setu-app.exe` (window), `setu-watch.exe` (HKCU Run key "Setu
  helper"), and Syncthing. Three things start at sign-in, and Setu only talks to Syncthing
  through `Client::discover()` reading an outside `config.xml`.

Requirement from the user: Syncthing is never a separate program, console, script or scheduled
task. It runs inside Setu, starts and stops with Setu, and only starts at sign-in if the user
turned that on in Setu. Setu does not talk to Syncthing as a separate entity (no REST API, no
HTTP port, no API key): Syncthing's code is built into Setu and Setu calls it directly.

### Decision

Build Syncthing's code into the Setu binary, call it directly, and make Setu one program with a
background (tray) mode.

1. **Syncthing compiled into Setu.** Add a Go module `engine/` in the repo that imports
   Syncthing (pinned to v2.1.7, MPL-2.0) as a Go library and builds with
   `go build -buildmode=c-archive` into a static library. `setu-core` links it statically
   (`build.rs`), so it ends up inside `setu-app.exe` / `setu-app`. No `syncthing.exe`, no DLL
   or `.so` beside it, no child process, no console.
2. **Direct calls, no REST.** The Go side runs Syncthing's engine in-process (`lib/syncthing`
   App with the GUI/REST service **not started**) and exports plain C functions that call
   Syncthing's own Go objects (`config.Wrapper`, `model.Model`, the event logger) directly:
   start/stop, my device ID, get/set folders and devices, folder defaults, options patch,
   ignores get/set, folder status, completion, need, local-changed, folder errors, versions,
   scan, connections, and an event subscription (a Go channel drained by a blocking
   `next_events(since, timeout)` call). Arguments and results cross the boundary as JSON
   strings in the same shapes Syncthing's REST API uses today; the Go side frees its own
   memory through an exported `free`.
   On the Rust side, `core/src/syncthing.rs` keeps its `Client` type and every method name and
   return type, but each method becomes a direct FFI call instead of an HTTP request. So
   `mesh.rs`, `apply.rs`, `watch.rs`, `accuracy.rs` and the rest do not change. `ureq`,
   `roxmltree`, `parse_config`, `default_homes` and `discover()` are removed.
   Nothing listens on 127.0.0.1:8384 or any other local port; only the sync port on the
   Tailscale address is open.
3. **One Setu process.** Fold `setu-watch` into `setu-app`: `setu-app --background` starts
   with no window, shows the tray icon, hosts Syncthing and runs the `watch::run` loop on a
   thread. Opening Setu from the tray shows the window in the same process. Closing the window
   hides it; **Quit** in the tray stops Syncthing cleanly (`stop()`, wait for it) and exits.
   A single-instance lock stops a second copy (second launch focuses the first).
4. **Setu owns the engine's data.** Keep keys, config and index in `%LOCALAPPDATA%\Setu\engine`
   (Linux: `$XDG_STATE_HOME/setu/engine`). Setu writes the config: GUI disabled, global
   discovery, relays, NAT, local discovery, usage reporting and auto-upgrade off. No API key and
   no GUI password exist.
5. **Start the engine only when Tailscale is up.** Before `start()`, wait until this computer
   has a Tailscale address (100.64.0.0/10 or fd7a:115c:a1e0::/48). If the address changes,
   update `listenAddresses` through the direct options call (existing `mesh.rs` code). No
   bind-error loop.
6. **Sign-in start is the user's choice, shown in Setu.** A setting "Start Setu when I sign in"
   (off until the user turns it on during first setup or in Settings). Windows: HKCU Run value
   `Setu` = `"<app>\setu-app.exe" --background`. Linux: XDG autostart
   `~/.config/autostart/setu.desktop` with `--background`. Setu writes and removes this itself.
   No scheduled tasks, no PowerShell, no systemd service.
7. **CLI.** `setu` (command line) never touches the engine itself. It sends its command to the
   running Setu over a local named pipe (Windows, current user only) or a Unix socket in
   `$XDG_RUNTIME_DIR` (Linux, mode 0600). If Setu is not running, it says so and offers
   `setu-app --background`.

Rejected:
- Bundling `syncthing.exe` as a hidden child process with a Job Object: still a separate
  program, which the user ruled out.
- Loading Syncthing as a DLL and talking to it over its loopback REST API: Setu would still
  talk to Syncthing as a separate entity through an HTTP port and API key.
- Rewriting the sync engine in Rust: far too large and would lose Syncthing's proven protocol
  and conflict handling.

### Migration (existing installs)

Run once by the new Setu on first start, with a dialog that lists every step and needs the
user's OK. Nothing is deleted before the new engine is proven working.

1. Find the old setup: scheduled task `\Syncthing (Setu)`, `%LOCALAPPDATA%\Setu\start-syncthing.ps1`,
   `%LOCALAPPDATA%\Setu\syncthing-gui-password.txt`, Run value `Setu helper`, a running
   `syncthing.exe` whose `--home` is `%LOCALAPPDATA%\Syncthing`; on Linux the
   `setu-watch.service` user unit and any `syncthing.service` user unit Setu enabled.
2. Stop the old Syncthing cleanly (one last use of its REST API, `POST /rest/system/shutdown`,
   with the key from its `config.xml`; this migration code is the only REST code left and is
   deleted in a later release), then wait for it to exit.
3. Copy (not move) `cert.pem`, `key.pem`, `config.xml` and the index database from the old home
   into the Setu engine home, so the **device ID stays the same** (no re-pairing) and folders
   are not hashed again. Only copy folders whose ID starts with `setu-f-` or is `setu-control`.
   Other people's folders stay with the old Syncthing and Setu tells the user they exist.
4. Start the embedded engine. Check: same device ID, every `setu-*` folder present, peers
   connect over Tailscale.
5. Only after step 4 passes: delete the scheduled task, the `.ps1`, the password file and the
   `Setu helper` Run value. Leave the WinGet Syncthing package installed and the old home in
   place (the user can remove them; Setu says how). If step 4 fails, restart the old setup and
   show the error. No partial state.

### Installer and packaging

- `packaging/windows/setu.iss`: ship `setu-app.exe` (engine built in) and `setu.exe`; drop
  `setu-watch.exe`, the "helper" task, the `Setu helper` Run value and the `taskkill` lines
  (stop Setu through its control endpoint instead). The "start at sign-in" checkbox sets the same
  value Setu's setting uses. Uninstall removes the Run value and stops Setu; it keeps the engine
  home and every synced file.
- `packaging/linux/`: replace `setu-watch.service` with the XDG autostart entry;
  `install.sh --uninstall` removes it.
- `.github/workflows/release.yml`: add Go (pinned) and a C toolchain for cgo (MinGW-w64 on
  Windows, gcc on Linux); `setu-core`'s `build.rs` builds `engine/` and links it. Local builds
  keep Go inside the working folder (`.tools`), not a global install.
- README: remove "Syncthing, running" from the prerequisites; Tailscale and Brahma stay.

### Licence

Syncthing is MPL-2.0. Linking its unmodified files into MIT Setu is allowed. Ship Syncthing's
licence text and a link to the exact source tag (and the `engine/` wrapper) with each release.

### Tests

- Go: `engine/` unit tests for each exported call against a temp engine.
- Rust unit: engine config (GUI off, discovery/relays/NAT off, tailnet-only listen addresses);
  Tailscale-address wait; FFI `Client` returns the same JSON shapes the old REST client did
  (golden files recorded from the current REST client before the switch).
- Two engines cannot share one process's Syncthing globals, so `core/tests/two_syncthings.rs`
  and `brahma_link.rs` start a second test process (a small test binary linking the engine) in
  a temp home on a free sync port, instead of `syncthing.exe`.
- Migration test: fake old home with a known device ID; after migration the ID matches and
  only `setu-*` folders moved; failure in step 4 restores the old setup.
- Windows check on the laptop (no VM): after install and migration, Task Scheduler has no Setu
  task, no `powershell.exe` or `syncthing.exe` is running, Task Manager shows only `setu-app.exe`
  (plus its WebView2 children while the window is open), and files still sync with the Linux
  computer.
- Linux check: same, with `ps` and `systemctl --user list-units`.

### Done when

- Syncthing's code is linked into `setu-app.exe`; no `syncthing.exe`, DLL or `.so` ships or runs.
- Setu calls the engine directly: no REST, no HTTP port, no API key. `netstat` shows Setu
  listening only on port 22000 on the Tailscale address.
- Quit in the tray stops all syncing.
- Nothing Setu-related starts at sign-in unless the user turned it on in Setu.
- No plain-text password or key on disk outside Syncthing's own `cert.pem`/`key.pem`.
- Existing laptop and Linux computer keep their device IDs and sync without re-pairing.
